# Private My Library sync — integrity audit

## Architecture being preserved

ManCardo remains local-first. Editing continues against the local working copy. The private cloud store is the durable cross-device replica for **My Library**. Shared Library remains a separate explicit publishing workflow.

## Phase 1 safety approach

This change starts in **shadow mode**:

- existing `localStorage` remains the source of truth for the live application;
- the whole My Library is mirrored into IndexedDB after local persistence;
- no existing track is deleted or rewritten during migration;
- no private track is uploaded until cloud storage and authentication are explicitly configured;
- the Device Check gains private-sync readiness checks;
- the cloud API refuses private data access unless an authenticated identity is present;
- D1 changes are additive only.

This gives us a safe way to validate managed-device behaviour before switching the primary local store or enabling automatic cloud writes.

## Risks audited and mitigations

### 1. Managed browser blocks IndexedDB
Risk: edits could appear saved but not be available for the future offline/sync engine.

Mitigation: Device Check performs a real IndexedDB open/write/delete test. Shadow mirroring never replaces the existing localStorage write.

### 2. Browser storage may be cleared by policy
Risk: company policy or private browsing can remove local data.

Mitigation: Device Check reports persistent-storage status separately. The future cloud copy is the durable replica; local persistence is not assumed to be permanent.

### 3. Cloud endpoint unavailable or blocked
Risk: local edits could be lost if Save depended on the network.

Mitigation: local save always completes first. Cloud status is independent. Future sync will queue changes rather than making the Save action network-dependent.

### 4. Missing or weak user identity
Risk: private My Library data could leak between users.

Mitigation: private API has no username-selector fallback. It only accepts a verified identity header from an authentication layer. Until authentication is configured, private data endpoints return `401` rather than weakening ownership controls.

### 5. Concurrent edits on phone and laptop
Risk: last-writer-wins would silently destroy work.

Mitigation: every mutation uses an expected `base_revision`. Updates only succeed when the cloud revision still matches. Stale writers receive `409 Conflict` and the current revision metadata.

### 6. Partial revision history
Risk: track data could update without a matching history snapshot.

Mitigation: D1 triggers create immutable revision rows as part of the same database mutation.

### 7. Corrupt or malformed payloads
Risk: invalid JSON or malformed track geometry could poison the cloud library.

Mitigation: server validates object shape, track id, type, segment/point structure, finite coordinates, latitude/longitude ranges, name length and payload size. D1 also enforces `json_valid()` and type constraints.

### 8. Accidental destructive delete
Risk: deleting on one device could permanently remove cloud data.

Mitigation: cloud deletion is soft-delete only and still requires the expected revision. Revision history remains available for recovery.

### 9. Clock differences between devices
Risk: timestamps from a phone or laptop can be wrong and break ordering.

Mitigation: cloud `updated_at` values are generated by the Worker, not trusted from the client. Sync cursors use server timestamps plus track id ordering.

### 10. Duplicate upload after retry
Risk: flaky mobile networks can cause repeated Save requests.

Mitigation: revision preconditions make a repeated stale write fail safely rather than creating unexpected later revisions. Future outbox work should add a mutation id for stronger idempotency.

### 11. Very large tracks
Risk: oversized JSON can exceed browser, Worker or D1 practical limits and make sync slow.

Mitigation: first implementation enforces a 2 MiB JSON payload ceiling per track and reports `413` with a clear message. This threshold can be revisited with R2 for exceptionally large payloads.

### 12. Local migration regressions
Risk: switching storage engines can strand existing My Library content.

Mitigation: this phase only mirrors existing localStorage into IndexedDB. It does not change `loadLibrary`, `persistLibrary`, import, edit or Save semantics.

### 13. Hidden data mismatch
Risk: the IndexedDB mirror could silently diverge from localStorage.

Mitigation: mirror records include a SHA-256 content hash when Web Crypto is available and a mirror timestamp. Device audit state exposes record counts and last mirror errors for validation.

### 14. Shared Library contamination
Risk: private draft tracks might accidentally become collaborative content.

Mitigation: private storage uses separate endpoints/tables and does not call the Shared Library publish API. Publish to Shared remains explicit.

## Cloudflare setup still required before cloud writes are enabled

1. Create a dedicated D1 database for private My Library data.
2. Apply `migrations/0001_private_library.sql`.
3. Bind the database to the Worker as `PRIVATE_LIBRARY_DB`.
4. Configure a real authentication layer that provides a verified user identity to the Worker.
5. Run Device Check from each target device/browser and resolve any critical failures.
6. Validate conflict behaviour with the same track edited on two devices before enabling automatic upload.

No destructive D1 operation is part of this phase.
